# 竞品设计观察与命名建议

日期：2026-09-12。目标：解决界面术语难理解、视觉过于通用的问题。本轮依据实际界面和官方演示提出设计方向；不将官网宣传或视觉判断当作效果测试。

## 结论

用户界面的“信源”建议改为“连接”：导航叫“连接”，管理页标题叫“应用与文件”，操作按对象写“连接飞书”“添加文件夹”；事项详情里的具体引用叫“来源”。插件开发及技术方案中的 Source、source_id 保留技术语义。

当前设计的问题来自信息组织：主区域给了口号和大空态，具体事项与动作缺少自己的表达方式。下一版应以“跟进清单 + 事项详情”为中心，通过来源记录、当前条件和缺少的一步体现产品特点。连接管理服务于这条工作流程。

## 名字怎么换

| 候选 | 好处 | 使用限制 | 建议 |
| --- | --- | --- | --- |
| 连接 | 简短、可操作，用户能理解连接自己的工具 | 单独作为对象名不够具体 | 作为导航名称 |
| 应用与文件 | 清楚覆盖在线应用、本地会话和文件夹 | 稍长，不适合高频按钮 | 作为连接页标题 |
| 工作应用 | 比信源自然，适合在线工具 | 难覆盖文件夹和手动导入 | 不作为总称 |
| 信息来源 | 意义明确，适合追溯引用 | 管理页仍偏描述性 | 简化为事项详情里的“来源” |
| 上下文 / 数据源 / 集成 | 对开发者有明确含义 | 用户仍需先理解实现概念 | 留在开发文档和高级说明 |

统一词汇：

- “信源与插件” → “连接”。来源连接和技能扩展不绑成一个普通用户必须理解的概念；完整扩展管理后续独立设计。
- “连接信源” → 依据对象写“连接应用”或“添加文件夹”。
- “尚未连接信源” → “尚未添加连接”。
- “信源断连” → “飞书连接已断开”，直接写出受影响的对象。
- “信源证据” → “来源记录”；核验结果写“已找到 PR，尚未找到反馈记录”。
- “Source Adapter”继续用于技术接口，不全局重命名数据库和代码里的 source。

## 竞品设计的好处与取舍

### Typeless：把主操作说清楚，并放在工作发生的地方

实机首页首先给出直接的行为指引，口述、翻译、提问分别对应具体键位；键位用键帽样式区分于说明文字。左侧主导航仅三项，读者容易看出这是一个围绕输入工作的专用工具。当前深色界面通过背景、侧栏、操作区的明度形成层次，应用图标提供识别点。

最值得学习的是“操作入口与用户意图对齐”。官方引导说明用户可在其他应用的文本框使用，不必将工作搬到独立聊天窗口。这不等于本轮已实测录音到回填全链路。

用于本项目：高频入口回答“现在要跟进什么”；选中事项后出现对应操作；日常使用不要求先到系统说明页。未来快捷面板应围绕快速查看和定位事项，具体键位需做冲突验证。

需要克制的部分：实机首页也包含大型标题、使用案例卡片、升级及推荐入口。它们适合 onboarding 和商业转化，不应整套搬到我们的日常事项清单。Typeless 不是所有页面都没有卡片；卡片是否合适取决于它承载什么动作。

### AirJelly：让工作记录和连接状态成为内容

连接与召回页用分组标题、分隔线和紧凑行组织内容；每行的应用标识、名字、状态、开关/同步操作相邻。Agent 访问与资料输入分栏，表达了两个不同的数据方向。相比给每个应用一个大卡片，这种结构便于同时比较多个连接。

首页以日期、时间线、人物、日程和询问组件构成个人桌面，大小不同的组件产生节奏；日期具有强识别，时间线包含时间、应用标识和事件，让界面围绕工作内容展开。官方文档也把时间线和背后的记录定位为回顾入口。

用于本项目：连接页用应用列表呈现；事项详情把来源、时间和状态变化放在一起，减少用户追查依据的跳转。借鉴视觉节奏时，让真正重要的事项变化占据主位。

需要克制的部分：图标轨道缺少常驻文字，初次使用需要学习；自由摆放组件会增加整理成本。我们首版仍应保留清楚的导航标签，采用稳定的清单布局，不先做可拖拽首页。

### MineContext：待办、上下文和询问可以同时看到

官方演示中，待办以可勾选的行排列，当前优先组有标签；完成后就地变化。最近活动提供上下文入口，AI 对话在侧边展开，待办区域仍保留在视野中。值得借鉴的是“处理时不丢上下文”，而非单独某种色彩。

用于本项目：左侧清单、右侧事项详情；详情先展示约定条件、已确认进展和来源记录，再放解释或询问入口。用户可以一边看承诺，一边判断是否真的完成。

需要克制的部分：演示中的多栏并置、长文本和宣传标题让首屏较拥挤；装饰渐变和 AI 文案不适合作为我们差异化的依据。它是业务结构的重要参照，视觉风格应独立设计。

## 当前版本具体哪里不对

| 当前设计 | 带来的问题 | 下一版处理 |
| --- | --- | --- |
| 英文副标题 + 大口号 + 介绍段落 | 主区域先解释产品，用户仍不知道此刻该处理什么 | 工作页直接使用“待跟进”等内容标题，品牌说明放到引导 |
| 巨大居中空卡片和菱形装饰 | 无内容时像通用模板；装饰没有表达事项语义 | 空态保留清单结构，用短说明和一个明确下一步 |
| 三句并列价值口号 | 占据空间但不帮助当前操作 | 移出日常页面 |
| 浅灰正文普遍偏淡 | 信息层级依靠“淡化”，降低阅读清晰度 | 主要信息保证对比，次要信息用字号、位置和留白区分 |
| 每个来源同尺寸卡片 | 连接数量增加后空间效率下降 | 用应用名、读取范围、同步状态和操作组成行 |
| 本地核心、SQLite、工程预览常驻主路径 | 实现状态抢占用户关注 | 开发诊断移到设置中的诊断入口；用户只见相关错误 |
| 导航按事项/信源/运行状态组织 | 用户工作、技术输入与工程诊断处于同一层 | 工作入口在主导航，连接与设置归为管理入口 |

这是一份设计判断，尚未经过可用性试验；“AI 感”在这里具体指这些可修改的结构，而不是单凭颜色判断。

## 下一版设计方向：清楚的跟进工作台

建议采用紧凑侧栏、可扫描清单和按需展开的详情。首页不需要默认聊天框，也不需要仪表盘式统计卡。以下是信息结构建议，未实现的能力在当前应用中不能伪装可点击或已连接。

| 区域 | 信息顺序 | 作用 |
| --- | --- | --- |
| 导航 | 待跟进 / 全部事项；底部连接、设置 | 以用户查看和管理的对象命名 |
| 清单行 | 当前状态、事项标题、项目/对象、截止依据、最后变化 | 快速判断需要关注的事项 |
| 事项详情 | 原始约定 → 条件完成情况 → 最新进展 → 来源记录 | 让核心差异体现在真实业务结构中 |
| 局部动作 | 确认、修改、稍后处理；按实际能力开放 | 操作紧贴要处理的内容 |
| 连接列表 | 应用/文件夹、读取范围、最近同步、异常、管理 | 清楚说明覆盖范围和运行状态 |

视觉建议：保留清楚的明暗对比，以文字、对齐和细分隔线构造层级；少量强调色用于选中项和确有意义的状态。来源可以显示真实应用图标，项目不要靠随机彩色胶囊区分。圆角和阴影依据控件用途统一，不让每段内容都成为卡片。

建议首轮尺寸基线供原型测量：导航宽约 160–180px；主文字 14–15px；清单标题 20–24px；行高随副信息约 52–64px。它们是原型起点，需在实际窗口和长中文标题下校准，不是已测试的最佳尺寸。

动效只用来解释状态变化、展开和切换；对点击立即给出反馈，远端结果随后更新。具体时长和减弱动态效果支持应在实现时验证，本轮不预设“用了某个动画参数就丝滑”。

## 改版验收方式

1. 用空态、有少量事项、长标题、断连、证据冲突五种状态检查设计，样例明确标为设计数据。
2. 用户能从一条事项看出“是什么、哪里来的、还差什么”；没有证据时写未找到，不写用户没做。
3. 首屏没有技术诊断和宣传段落占据主内容；只有与当前问题有关的操作。
4. 验证键盘焦点、文本对比、窗口缩窄和系统减少动态效果，不用截图好看代替交互验证。
5. 记录从查看事项到找到原始承诺所需的操作，以及一次误判的纠正路径；与现版比较。

本轮先统一界面词汇并形成改版依据。后续页面结构重做应以这套信息层级推进，避免只改配色和装饰。
