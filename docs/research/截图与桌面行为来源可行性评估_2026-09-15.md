# 截图与桌面行为来源可行性评估（X05）

结论：本版本不接入持续截图或桌面行为监听。未来可以试验用户主动的单次窗口/区域截图；Browser Use、Computer Use 的自动操作不属于来源采集授权，也不纳入本次产品范围。此项交付是接入决策，尚未开发截图连接器。

## 价值与代价

| 方案 | 可补充的信息 | 主要代价 | 决策 |
| --- | --- | --- | --- |
| 用户主动截图 | 无 API 应用中的工单、报错、交付页面 | OCR 会误读；图片含无关私人内容；缺稳定消息 ID | 后续隔离原型，单次确认 |
| 连续屏幕采集 | 跨应用工作上下文 | 大量无关信息、资源消耗、去重及删除困难 | 本版不做 |
| Browser Use | 用户指定页面的结构化内容 | 登录态、网页提示注入、页面变动、越域访问 | 优先专用连接器；不自动控制用户浏览器 |
| Computer Use | 无 API 软件的可见交互 | 读取与执行混在一起，可能误点击发送/删除 | 不用于后台采集，也不替用户操作 |

## 技术可行性与授权

Electron 的 `desktopCapturer` 在主进程枚举窗口/屏幕；通过系统选择器申请捕获，不向渲染进程开放任意窗口读取或 Node API。macOS 屏幕捕获需要系统同意，系统权限与 BUGU 内的项目、模型授权分开记录。[Electron 官方接口](https://www.electronjs.org/docs/latest/api/desktop-capturer)

Windows 的 `Windows.Graphics.Capture` 支持用户选择捕获目标；未来原型应先验证 Electron 封装的选择和取消行为，只有证实封装有缺口再考虑单独原生模块。[Microsoft 屏幕捕获文档](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture)

Linux Wayland 使用桌面 Portal 的选择流程和 PipeWire 流，不能假设各桌面环境能直接枚举同样的窗口；取消请求、选择单屏/窗口和无后端环境须独立测试。[XDG ScreenCast](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.ScreenCast.html)

以上是官方接口能力与本项目的设计推论，本轮没有申请用户的屏幕录制权限，也没有运行实际跨平台捕获验收。

## 限定流程

1. 用户指定项目并主动发起截图；每次由系统或明确的选择器选目标。
2. 截图只进入本机临时预览，用户可取消或遮挡；不同时采集音频、键盘、剪贴板。
3. OCR 原文与选定模型、拟发送片段一起预览。模型开关关闭时仅允许本地保存，不能自动上传或后台补发。
4. 用户确认收录后才形成来源事件，附采集时刻、图片哈希、原图及 OCR 关联；原文中的指令全部是待分析数据。
5. 任务状态仍按当前平台的候选、证据和人工状态规则处理；截图里的“已完成”只是一条待复核陈述。
6. 撤销权限终止采集；删除图片及派生文本的生命周期、迁移与备份规则完成后才允许上线。

原型放行条件：三平台选择/取消行为明确；图片预览与遮挡可靠；零权限时零采集；模型关闭零外发；可定位原图引用；连续采集不存在；外部发送/点击不存在。原型指标需测 OCR 引用准确率、单次延迟、图片内存与磁盘占用，本次不预填成绩。

已回写 PRD。本项只关闭可行性评估，不将截图接入、浏览器插件或自动操作需求标为完成。
