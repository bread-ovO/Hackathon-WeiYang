## 1. 评审结论

继续采用平台无关的 TypeScript 领域与应用层、utilityProcess 核心和 SQLite。优先补全接收、版本和恢复语义，再连接真实业务处理。当前基础可复用，但原表中的部分验收跨越数据层与业务层，应分别记录“基础验收”和“联合验收”，保持父需求的完整验收要求。

| 需求 | 代码事实 | 评审结论 |
| --- | --- | --- |
| S01 | v1 Schema 只有来源、外部 ID、修订、发生时间、角色和正文 | 新增版本化事件类型、来源追溯和有界页信封；保留明确的旧版读取路径 |
| S02 | 只有最小 tasks、source_events、jobs、source_instances 表 | 增加四维状态、条件版本、证据引用、人工决定与事项修订；实施保守迁移 |
| S03 | 每次单事件、作业和游标同事务 | 连接器已有分页返回类型，接收应升级为整页原子提交、检查点比较和持久回执 |
| S04 | 三元唯一约束及冲突忽略 | 同键不同事实应拒绝；事件、作业、业务操作分层去重，最终联验 V05 |
| S05 | 只有 attempt、lease_until 等列 | 增加原子领取、租约版本、有限重试、执行器和受保护的结果提交 |
| S06 | 无项目检索字段和索引 | 项目范围先过滤，再做确定性分词、标识符查询及 FTS5；需标注集验证 |
| S07 | 发生和接收时间已存储，无因果与身份映射 | 补齐时间依据、修订顺序能力、命名空间及映射版本；计划更新联验业务层 |
| S08 | 仅有 Schema 字符长度限制 | 同时限制读取、页、队列和所有自动写入；磁盘额度包含 WAL 等受管文件 |

静态证据：[contracts](../../packages/contracts/src/index.ts)、[storage](../../packages/storage/src/index.ts)、[application](../../packages/application/src/index.ts)、[connector](../../packages/connectors/src/index.ts)、[现有集成测试](../../tests/storage-integration.ts)。当前测试证明单事件事务、事件去重与正常关闭重开，不证明分页 ACK、作业强杀恢复或事项层幂等。

五项优先纠正的设计问题：

1. 不能把整页末尾游标随第一条事件提交，否则页内故障可能跳过尚未落库的记录。
2. 同一修订若携带不同事实，不能用冲突忽略静默接受。
3. 内容哈希不能独自证明修订身份：A→B→A 的真实再次编辑可能被误判成旧输入重放。
4. 核心进程能重启，不等于作业可恢复；旧租约执行者必须失去提交资格。
5. 数据字段齐全，不等于“人工选择不被覆盖”“一次业务变更”“迟到消息不改新计划”已通过。

运行时、表和对外事件分别版本化：事件 schemaVersion 不等于 SQLite user_version；流水线、分词和规则版本也不能共用其中之一。

## 3. S01：标准事件协议

### 3.1 v2 envelope 与信任边界

沿用 camelCase。新增 v2 parser，保留 v1 解码器；未知版本及额外字段拒绝。下表是 Schema 的设计输入，不作为第二套手写类型真相。

| 字段组 | 建议字段和语义 |
| --- | --- |
| 版本与对象 | schemaVersion=2、sourceInstanceId、externalId、revision；来源实例与外部 ID 定位对象，revision 为不透明修订标识 |
| 变化类型 | eventType：created、updated、retracted、deleted、observed；observed 只表示快照，不能推断此前发生过什么 |
| 时间 | occurredAt、可空 sourceUpdatedAt、timeBasis；日期带明确偏移，未知用显式 unknown/null，禁止拿本机接收时间补造发生时间 |
| 内容 | payload 使用有判别字段的 message / delivery / tombstone 结构；保留 message 的 user/assistant/tool/system 角色，GitHub 平台事件不强行伪装成用户发言 |
| 身份与定位 | provenance：adapterId/version、来源内账户/租户/会话或资源 ID、原始角色/作者引用、原始时间与时区依据、修订依据、可选上游通知 ID |
| 修订能力 | revisionBasis：上游稳定修订、已验证顺序/前驱、持久观测序列或 snapshot-only；有前驱时保存 supersedesRevision |
| 宿主补充 | receivedAt、规范内容指纹、实际授权版本和处理 trace；由宿主生成或核定，输入不能自行声明读取许可 |

payload 禁止任意无界 object；每种来源内容均使用明确 Schema。新增类型通过版本兼容策略扩展。墓碑必须定位目标对象，可不带正文；“删除”不等于“用户取消事项”。受控资源 ID 仅用于追溯，不给 renderer 任意文件读取能力。全文或片段引用约定按原文 Unicode code point 的半开区间计数，指明事件修订；JS UTF-16 索引需显式转换，并以 emoji 样例验证。

### 3.2 兼容与修订身份

旧 v1 可显式转换为 legacy/observed，保留原字段并标注追溯不完整，不能默认成 created 或补造作者。迁移保留旧事件原始记录；转换器仅用于旧数据和显式兼容调用，真实来源启用 v2 仍需来源契约验证。

规范指纹包含 eventType、事实 payload、角色、语义时间和稳定对象定位；不包含本次 receivedAt、trace、分页 stream、batchId 或连接器软件版本。属性键顺序、时间等价表示按版本化规范序列化，正文原样保留，不因搜索规范化改变原文。记录 fingerprintVersion，迁移时按版本比较，不能直接拿不同版本哈希判定冲突。

优先使用上游稳定修订。内容哈希只判断内容是否相同；无可靠修订的来源必须通过受测的持久观测序列或快照模式适配。首次支持某来源前，用 A→B→A、同时间两次编辑、轮转和重放验证；无法区分的情况保存覆盖限制，不承诺完整编辑历史。

## 4. S02：事项、条件与证据模型

### 4.1 四维状态

| 维度 | 值 | 约束 |
| --- | --- | --- |
| 收录决定 | candidate / accepted / ignored | 新写入必须显式给出；候选不自动成为正式待办，忽略不等于取消 |
| 业务状态 | todo / in_progress / waiting / completed / cancelled | accepted 必须有业务状态；未正式收录的候选可为空，忽略时不抹去原有业务历史 |
| 证据状态 | unknown / partial / sufficient / conflict | 与业务状态独立；人工完成允许 unknown，迁移和模型不得伪造充分证据 |
| 展示属性 | archivedAt 或空 | 归档只改可见性，保留其他状态 |

### 4.2 建议实体与数据库约束

| 实体 | 最小内容与关键约束 |
| --- | --- |
| source_instances / source_streams | 来源与账户命名空间、授权版本；每个 stream 独立 cursor、cursorVersion、scopeEpoch、健康状态 |
| source_events / source_object_heads | 不可变事实修订及内容指纹；三元唯一键；对象当前修订/墓碑/顺序不确定状态和 generation |
| projects / identities / identity_mappings | 来源内身份、显式确认的跨源映射、映射版本及撤销关系；名称不是唯一身份 |
| tasks | 四维状态、projectId、ownerRef、taskVersion、currentCriteriaVersion、manualVersion、legacy 标志 |
| criterion_sets / criteria | 每事项不可变条件集版本；条件具有稳定 ID，保留提出条件的原文/人工来源 |
| evidence_links | 精确引用 taskId、条件集版本、criterionId、事件修订及片段；support/oppose/related 与 valid/invalid/needs_review 分开 |
| decisions / decision_inputs | actor、操作、理由、精确输入引用、规则/模型/提示版本、预期版本和 operationId；追加记录 |
| manual_overrides / task_revisions | 被保护字段/关联/操作范围、替代关系、人工版本；每次有效修改的前后版本及决定引用 |
| processing_runs / operation_commits | 持久处理身份、已验证 proposal、输入集和流水线版本；operationId 唯一并保存已有结果 |
| notification_outbox | 唯一逻辑通知 ID 与 decision 引用，供后续提醒模块消费；不等于系统通知已实现 |

证据到条件使用复合外键，确保引用的条件属于同一事项及版本；不能只分别验证几个 ID 存在。事件修订不存在、跨事项条件、非法状态或版本倒退应由外键/CHECK/唯一约束及应用事务共同拒绝。SQLite 的复合外键要求父键具有对应唯一性，见 [官方外键说明](https://www.sqlite.org/foreignkeys.html#composite_foreign_key_constraints)。

事项修改使用命名用例，禁止 renderer/模型提交任意 SQL、表名或自由 JSON patch。自动提交核对 task、条件集、manual、身份映射及所用来源对象 generation；事件撤回或顺序变为不确定时，旧 proposal 不能在重评估完成前继续用于自动完成。接收事实可更新对象修订有效性，业务状态变更仍经过领域规则。

人工保护只覆盖用户选择的字段、关联或操作，直到被明确撤销或新的人工决定替代；不以永久整项锁阻止其他合法进展。条件变更生成新版本，旧证据保留历史但不自动满足新条件。自动完成策略、合并拆分、撤销语义分别与 V/H 模块联合验收。

### 4.3 迁移策略

从现有 v1 拆出顺序迁移文件：事实/检查点 → 事项证据 → 作业 → 检索 → 容量与诊断。每个迁移在编码时分配递增 DB 版本，禁止所有改动反复重写 v1 建表脚本。

迁移前停止业务写入，创建并检查一致性备份及空间余量；备份失败则不开始迁移。使用 SQLite 一致性备份能力，不复制仍活跃的裸 DB。事务迁移成功并完成约束检查后更新版本；异常停止启动业务写入，保留可恢复诊断。依据 [SQLite backup](https://www.sqlite.org/backup.html)；驱动 API 和实际打包环境需在实现时验证。

保留旧事件 ID、修订、内容、接收时间、来源游标和作业身份；原来源游标映射到 legacy stream。旧来源补为未验证来源，禁止迁移授予新权限。旧事项无来源/条件/人工记录时，保存 migration baseline；保留原业务状态与归档，收录未知仅允许 legacy 行暂为空，无有效引用的证据投影置 unknown，原值保留在基线。迁移记录 actor=system_migration，不能伪称人工或 AI 已确认。legacy 事项自动处理资格默认关闭，待明确核验。

现有 done/failed 等作业映射保留原结果和尝试次数；不得把失败旧作业一律重置为待处理。验证迁移重复打开、每步故障回滚、未来版本拒绝及旧程序拒绝新库。恢复备份必须报告备份后的数据损失范围；完整发布恢复界面仍与 T06/T07 联验。

## 5. S03：整页事务与持久确认

建议应用入口为 receivePage(input, trustedContext)，连接器只提交数据。输入 Schema 包含 sourceInstanceId、streamId、scopeEpoch、batchId、expectedCursorVersion、nextCursor 和有界 events 数组；授权范围来自可信上下文，并与核心登记的版本核对。

同一来源可以有多个独立会话、仓库或回补 stream。cursor 是不透明值，不比较其字典或数值大小；通过宿主维护的 cursorVersion 防止并发覆盖。来源对象的去重身份不包含 stream，避免重叠采集重复建事件。重设来源范围产生新 scopeEpoch；不能静默复用旧页。

一个短写事务按顺序执行：

1. 核验当前来源、stream、授权 epoch，以及每条事件是否在已授权范围内。
2. 按 stream＋epoch＋batchId 查询持久 receipt。相同 pageDigest 返回原提交结果并附当前检查点，不再更新游标；相同 batchId 不同 digest 拒绝。
3. 新 batch 检查 expectedCursorVersion；错误返回 STALE_CHECKPOINT，不部分落库。再按实际新增事件和写入预算检查资源准入。
4. 保存整页所有新修订、事实有效性投影及应有作业；批内和库内同键冲突均中止整页。
5. CAS 更新 cursor 和 cursorVersion，写入 receipt，提交后才生成成功 ACK。

receipt 保存规范页摘要、事件/重复计数、提交检查点版本和接收时间，唯一键覆盖来源/stream/epoch/batchId。pageDigest 包含事件语义、预期检查点和 nextCursor，不含每次执行生成的时间/trace。回执保留策略要有界；已清理旧回执的过时页返回 STALE_CHECKPOINT，调度器读取当前检查点重新拉取，不推测成功或回退。

查已提交 receipt 要早于检查旧 expectedCursorVersion，否则“已提交但 ACK 丢失”的合法重试会误报版本冲突；真实授权校验仍先执行。连接器收到回执后仅以宿主当前检查点调度，不能用旧回执中的游标回退。空页、全重复页可合法推进一次；含非法记录的页不静默跳过。单事件入口如保留，应包装成单元素页并提供正确检查点，禁止保留无条件写游标的旧路径。

默认同 stream 串行拉取；CAS 用于故障和并发兜底。SQLite 同时仅一个写事务，显式短事务领取/接收可使用立即写事务；忙错误进入有界重试，不能在事务内等待网络。见 [SQLite 事务说明](https://www.sqlite.org/lang_transaction.html)。

## 6. S04：三层幂等

| 层次 | 稳定身份 | 行为 |
| --- | --- | --- |
| 事件事实 | sourceInstanceId＋externalId＋revision | 同指纹为重复；不同指纹返回 REVISION_CONTENT_CONFLICT，保留旧事实并拒绝整页 |
| 处理作业 | eventRevisionId＋pipelineVersion＋显式 runGeneration | 普通重投不增加作业；规则升级或人工重处理创建明确的新运行并记录前序关系 |
| 业务操作 | 处理单元持久 operationId＋规范输入集＋目标操作及策略版本 | 重试恢复同一身份；原子提交去重记录及业务结果，重复返回原结果 |

首版每个事件修订建立一个根作业，阶段进度保存在 processing_run，避免立即引入多级队列。未来增加多阶段作业时再扩展唯一键。内容变化以新修订追加，禁止覆盖旧正文；撤回/删除触发证据重评估，不能直接销项。

operationId 在第一次计算前持久确定，新建事项的目标 ID 也由处理单元稳定分配；不能用每次随机模型结果、attempt 或刚读取的 taskVersion 生成全新幂等身份。输入集或目标发生真实变化属于显式新处理版本；旧建议被标记 superseded，再检查有效人工决定。幂等不意味着所有不同修订只允许一次变更，而是同一业务操作的重试只提交一次。

事件和作业层可单独验收。事项版本、decision、task_revision、operation_commit、逻辑 outbox 不重复，必须接 V05 真实提交入口验收；使用计数器或固定假结果仅证明测试装配。

## 7. S05：持久作业、租约与结果提交

建议状态：pending → running → done；暂时失败进入 retry_wait；永久失败或预算耗尽进入 dead；授权/资源问题可进入 paused，显式取消进入 cancelled。状态迁移须集中定义，终态不得由普通轮询自动复活。

作业保存 leaseOwner、单调递增 leaseToken、leaseUntil、attempts/maxAttempts、nextRunAt、lastErrorCode、terminalReason 和 processingRunId。原子领取/接管时递增 token 和 attempts；续租不增加次数。达到次数上限的过期 running 直接进入 dead，否则“执行即崩溃”会无限恢复。

续租、失败结算、写入阶段结果及最终提交都核对 owner、token、running 状态和未过期租约。旧执行者的成功响应不能绕过检查；AbortSignal 仅用于停止无用工作。外部调用在事务外，结果经 Schema、引用及授权版本校验；允许推理请求被重复发出，不承诺外部调用恰好一次。

最终提交由一个存储事务完成：有效租约 → 当前授权与业务/条件/人工/映射/证据版本 → 已有 operation 查询 → 新业务决定、修订、索引及 outbox → operation 结果 → job.done。无业务变化也保存可解释 outcome 后完成作业。不存在“先改事项，再单独 ACK job”的写入路径。

超时/限流等瞬态错误使用有上限指数退避与抖动；格式错误给有限重试预算；输入永久非法进入 dead；撤权进入不可继续执行的 paused/cancelled，重新授权需校验新 epoch。版本冲突丢弃过时 proposal 后有界重算，冲突也占处理预算，禁止无限重试。

Clock 和 Random 注入；持久调度使用 UTC，进程内超时使用单调计时。休眠跨越租约后旧结果拒绝，时钟异常产生诊断，不能通过修改时间绕过 fencing。可先以租约 60 秒、20 秒续租、最多 5 次尝试、1 秒基础/60 秒上限退避作为测试和探针初值，参数均待负载验证，不是已测资源承诺。

基础恢复测试使用可控 handler 验证领取和错误路径；真实模型、业务提交及撤权取消分别与 A07/V05/Q03 联验。核心三次自动重启耗尽时应显示 CORE_UNAVAILABLE，作业保留于数据库，用户重启后继续恢复。

## 8. S06：中文与混合文本候选检索

搜索投影独立于原文：NFKC、英文小写、版本化项目词典最长匹配，未知连续中文补双字切片；单字查询仅在明确限定集合内回退。保留完整代码/仓库/路径标识符，再补 camelCase、snake_case 等拆词。对大小写有身份意义的代码对象保留原值，规范匹配只作为候选。

使用普通 search_documents 保存任务/条件当前文本及 taskVersion、tokenizerVersion，另建标识符精确索引和 FTS5 external-content 索引。默认 unicode61 不承担中文词语分割；trigram 的全文查询无法独自覆盖少于 3 字符的输入，因此不以它作为唯一短词方案。见 [FTS5 tokenizer](https://www.sqlite.org/fts5.html#tokenizers)。

每条查询路径在排序和 LIMIT 前约束已授权来源及已确认项目；未知项目只在显式来源范围补候选，否则返回范围不确定。不得全库取前 N 后再做权限/项目过滤。排序依次考虑精确对象、字段权重/BM25、更新时间及稳定 ID；关联决定仍属于 A04，检索分数不直接合并事项。

初始候选上限建议 20；未命中或索引降级时，只扫描同项目近 90 天最多 200 条，再返回不超过 20 条并带回退原因。参数可配置且需评测。输入按文本处理，构造并转义 FTS 查询，不能把用户输入作为原生 MATCH 表达式执行；限制字符/字节数、词数和候选数量。

事项/条件投影与搜索文档、FTS 更新放同一事务。外部内容 FTS 的一致性由应用维护；新增触发器不能替代历史回填，迁移和分词版本升级要重建索引。重建未就绪时显示降级并用有界回退，删除后的派生清理联验 Q05。见 [FTS5 外部内容表一致性](https://www.sqlite.org/fts5.html#external_content_tables)。

建议冻结至少 120 个合成标注查询案例，包含预期候选、项目、查询组及负例；开发集与保留验收集分开。拟定门槛为关键身份/隔离案例全过、整体 Recall@20 ≥95%、每个语言组 ≥90%；无相关候选的负例另报误候选情况，不混入 Recall 分母。Recall 按每查询期望集合命中比例求宏平均，同时报告各组分母、精确命中排名、回退比例及漏召回清单。目标尚未测量，合成集结果不能宣传为真实来源准确率。

在 1 万条合成事项上记录设备、Electron/SQLite/分词版本、冷暖查询 P50/P95、索引空间和回填耗时。先建立基线，再冻结性能预算；未达标优先调整有界查询和索引，不预先引入向量库。

## 9. S07：时间、身份与迟到事实

发生时间、来源修订时间与本机接收时间分开。归一为 UTC 的同时保存原值、偏移/时区及解析依据；UTC 偏移不等于完整时区规则。未知时间不造值。“周五”等截止由 A02 按消息发生时间与可确认时区解释，有歧义留空并保留原因，不能按重放当天解释。

revision 永远是不透明身份。仅当适配器声明且验证过序列、前驱或可靠修订时间语义时更新对象当前修订；时间相同无可靠顺序时保留不确定性，不把字符串最大值或最后到达者当最新。receivedAt 用于处理延迟，不能裁决计划版本。

source_object_heads 记录对象当前有效修订/墓碑/不确定及 generation；接收修订时根据可验证因果更新，晚到旧正文不得复活先到撤回。对未知目标修订的对象级墓碑保守保持不可自动用作完成证据；只有可证明的恢复/新对象才能解除。不能以“时间旧”丢弃反证或撤回；它们仍进入相关事项重评估。自动 proposal 提交时核对实际引用是否仍有效，而不仅检查任务版本。

来源实例绑定 provider、tenant/account 稳定 ID；externalId 必须在其来源命名空间唯一，若上游仅会话内唯一，由适配器把会话/对象类型纳入稳定命名空间。来源卸载重装可显式恢复原实例，否则生成新实例并记录覆盖差异，不能仅凭名称合并。人物、项目和对象各自保留来源 ID，跨源映射由显式用户确认产生 actor、scope、mappingVersion 和 supersedes；撤销映射使依赖它的旧 proposal 失效，映射本身不扩大读取权限。

可单独验收时间规范化、命名空间和对象顺序 reducer。“周一承诺→周二改期→周一旧消息迟到后新计划仍有效”，须与 A02/A04/V01/V05/H01 的真实计划更新联合回放，不能只验证数据库排序。

## 10. S08：背压、容量与诊断

接收和所有自动结果写入共用 ResourceAdmissionPolicy。连接器在读取/解压阶段限制体积，核心再次检查完整事件/页的 UTF-8 字节数、字段和数组上限；Schema maxLength 仍作为结构限制，但不是字节额度。

| 资源 | 建议准入方式 |
| --- | --- |
| 事件/页 | 初始探针配置：单事件 256 KiB、单页 2 MiB 且最多 100 条、游标 4 KiB；全部可配置并按边界验收 |
| 队列 | pending/running/retry_wait/paused 计入未完成工作；按本事务新增去重作业计额，初值高水位 10,000、低水位 8,000 |
| 磁盘 | 统计 DB、WAL、SHM、原文、模型缓存及受管备份；另检查所在卷余量和单事务增长预算 |
| 后台处理 | 领取前及提交阶段结果/修订/索引/outbox 前检查额度；超额暂停新写入，避免停采集后作业继续写满 |
| 诊断与恢复 | 有界错误记录、原因/恢复条件、暂停来源/全局范围、队列最老等待时长；不得把诊断自身写成无限增长源 |

队列容量在事务内重新核对；达到高水位暂停采集，降到低水位恢复，暂停原因需分别追踪。重复 receipt 不消耗新工作额度；全重复的新页可能仍写回执/检查点，因此仍受磁盘预算约束。dead 作业不占活动队列，但仍计磁盘并受诊断保留策略约束。

磁盘使用物理测量加保守写入预留，处理数据、索引和 WAL 开销不能仅用正文大小估算。总额度和安全余量须在合成负载探针后冻结；测量滞后和同卷其他程序写入会导致突然满盘，因此必须处理真实 SQLITE_FULL/IO 错误，不能承诺目录字节数瞬时绝不越线。额度超限时保留读取，人工写入失败也必须明确反馈，不能显示保存成功。

max_page_count 只限制数据库页数，checkpoint 也不是 WAL 大小硬上限；长读事务可阻止 WAL 复用。限制读事务时长、监测 checkpoint 进度，在受控空闲阶段回收，不删除活动 WAL。见 [SQLite limits](https://www.sqlite.org/limits.html#max_page_count) 和 [WAL 大小控制](https://www.sqlite.org/wal.html#avoiding_excessively_large_wal_files)。

单条永久超大事件暂停对应来源，保留最后完整接收检查点和有界定位；不静默截断/跳过、不快速无限重试。可由适配器缩小页、修复解析或用户调整配置后，从同检查点重拉。无法可靠分割的一页不得提交前半页并使用整页末游标。物理磁盘已满导致诊断无法落库时，通过进程内状态和返回错误显示暂停；重启重新探测容量并从持久检查点恢复，不谎称暂停记录已持久化。

扩展受 Schema 约束的 health DTO，分开 coreStatus 与 processingStatus，新增暂停原因/范围、队列、占用/额度、检查时间及允许恢复动作。core ready 不等于正在采集；采集暂停不等于事项完成。IPC 回复也要验证，renderer 不收到真实路径、凭据、原文或任意文件能力。来源页面显示暂停原因和恢复状态，与 U03 联验；基础查询接口存在不代替 UI 验收。

## 12. 验收与状态管理

每项结果保存基线提交、环境、配置、样例版本、断言结果和遗留问题。需求表仍使用现有状态；另附基础/联合证据说明，不创建含糊的“接口已完成”口径。特别是 S03/S04 原有待验收状态不能凭旧测试直接升级完成。

实施后的共同门槛：相关单元与集成测试、typecheck、check:boundaries；基础改动运行 pnpm check。原生依赖或打包变更再运行 pnpm package:dir；仅新增普通表/TS 用例不据此宣称完成签名、加密或跨平台发布。全局 pnpm 不可用时使用 npx --yes pnpm@10.34.5。

数据库测试必须使用隔离临时目录和 Electron 的原生 ABI；强杀使用专门测试子进程及明确阶段屏障，不杀用户运行中的应用。确定性测试注入时钟、随机数、磁盘探针和 handler；磁盘故障既做故障注入，也在隔离库验证实际 SQLITE_FULL，不填满用户磁盘。真实来源联合验收另用已授权、脱敏样例；本轮不读取个人聊天、代码历史或凭据。

还需通过探针冻结的参数：来源修订/分页能力、输入体积、租约/超时预算、分词词典、召回阈值、磁盘总额/安全余量、诊断/回执保留周期及性能预算。本文给出可执行初值或决策方法，不将未测数值写成达标结果；这些参数不阻碍先完成隔离样例下的协议、事务和故障测试。
