## 当前实现补充（2026-09-15）

任务发现已统一为真实模型提取与复核；来源处理器不再通过关键词或正则创建候选。`task-analysis-v3` 从会话开头分段处理，携带来源支持的已有任务 ID，经过逐字引用、项目和授权校验后事务保存。v25 增加分析窗口进度，保护重启与追加内容的重放幂等。具体流程图、预算及限制见 [真实模型任务提取与分段复核](../engineering/真实模型任务提取与分段复核_2026-09-15.md)。

以下总体设计含后续目标；目前模型阶段为建议，不自动修改业务完成状态。跨来源自动归并、完整条件核验不能视为已完成。

## 推荐结论

**首版采用 Electron + React + TypeScript，构建本地优先的模块化桌面应用；SQLite 作为事项、证据和处理记录的唯一权威存储。模型负责理解和建议，领域核心负责校验、状态更新与人工纠正保护。**

建议先做 macOS，连接飞书限定范围、一种本地 AI 会话和 GitHub 交付记录。macOS 优先依据当前试用环境，尚未代表目标客户的平台分布。功能扩展以 AirJelly 为参照，采集—处理—消费的分层借鉴 MineContext。首版不依赖 Python 服务、独立向量数据库或自建消息队列。

真正需要先攻克的是“可授权接入 → 连续关联同一事项 → 根据当前条件核对证据 → 可纠正且可恢复”，而不是先搭通用 Agent 平台。只读结构化来源跑通后，再评估屏幕、OCR、外部 Agent 上下文与更自由的代码插件。

## 依据、目标与不变量

### 已核验事实与设计判断

前序实机与静态调研发现：AirJelly 2.0.0 使用 Electron、React、SQLite 和 LanceDB，包含 Skills、上下文桥接及事项关联逻辑；静态代码中的行为不能全部当作已经实测的产品效果。MineContext 在所审阅提交中采用 Electron/React/TypeScript 与 Python 后端，并分离采集、处理和内容消费。详见项目 research 文档及证据索引。

MineContext 参照固定在提交 171c7a9ea8091e326ddcf0f10718aa1b58c83c65；后续引用代码应保留许可证与来源记录。本文借鉴公开架构思路，不复制 AirJelly 私有实现。候选依赖在开发启动时锁定兼容且受维护的版本，不照搬竞品版本号。

设计目标对应 PRD R01–R10：限定读取、持续事项关联、证据核验、低打扰、人工纠正、插件扩展及删除恢复。首版不做跨设备同步、团队协作数据库、默认屏幕/麦克风采集，也不替用户发送消息或执行业务操作。

必须保持的约束：

- 每次自动状态变更均能追溯输入修订、条件版本、规则和模型版本；没有新活动不等于完成。
- 来源权限决定数据可见范围；看不到证据不等于事情没有发生。
- 插件和模型不能直接写事项状态；人工编辑与自动判断发生冲突时，自动结果重新计算。
- 重复输入与故障重试不重复产生业务变更；模型调用失败不静默丢失事件。
- 删除覆盖原文和派生内容；“本地保存”不等于“推理数据不离开本机”。

## 技术栈如何选

### 选择标准与备选方案

按当前产品约束排序：接入与闭环开发效率、状态正确性和可回放性、桌面分发与后台稳定性、扩展成本、资源占用。团队语言经验尚未核实，因此不把“团队熟悉某语言”作为既定理由。

| 决策 | 推荐与理由 | 备选及代价 | 何时重新评估 |
| --- | --- | --- | --- |
| 桌面框架 | Electron：桌面生命周期、Node 生态与 TS 适配器组合一致，符合已观察的 AirJelly 扩展方向 | Tauri + Rust：系统 WebView 和能力边界值得评估，但需增加 Rust/原生接入与平台适配工作；不能未经测量承诺资源收益 | Electron 的实测资源预算不达标，或团队已有成熟 Rust 能力 |
| 应用后端 | TypeScript 领域核心 + Electron utilityProcess；同一语言维护契约和业务逻辑 | Python + FastAPI：利于直接复用 MineContext Python 模块，但多运行时打包、端口及进程生命周期增加负担 | 确定复用大量 Python 处理链、OCR 或本地模型生态收益超过成本 |
| 数据持久化 | SQLite + 显式 SQL 迁移；事务管理事项、事件与作业 | PostgreSQL：适合服务端共享协作，但增加个人桌面的运维依赖 | 团队共享、跨设备同步成为明确需求 |
| 检索 | 首版 SQLite FTS5 + 项目/对象过滤 + 模型候选判断 | LanceDB 等向量索引提高语义召回的潜力，同时引入索引一致性、模型版本和磁盘管理 | 标注集显示召回瓶颈确实来自语义检索 |
| 后台调度 | SQLite 持久作业表、租约、重试和通知 outbox | Redis/BullMQ 或云队列增加服务依赖 | 服务端规模与多节点调度确有需要 |
| AI 编排 | 明确阶段的流水线 + ModelProvider 接口 | 通用 Agent 框架更灵活，但自由规划不利于约束状态写入和定位误判 | P1 的草稿或上下文工具场景产生实际需求 |
| 扩展 | 可信内置适配器 + 可安装的声明式来源插件 | 任意 JS/Python 插件覆盖更广，但独立进程本身不构成安全沙箱 | 完成代码审查、权限执行和隔离方案验证后再开放 |

Electron 的进程隔离与安全配置参考[官方安全指南](https://www.electronjs.org/docs/latest/tutorial/security)和 [utilityProcess](https://www.electronjs.org/docs/latest/api/utility-process)。Tauri 的能力模型可作为后续候选，见[官方安全文档](https://v2.tauri.app/security/)。上述选择是本项目的取舍，不是两种框架的性能排名。

### 推荐组件清单

| 层次 | 首版建议 | 使用边界 |
| --- | --- | --- |
| UI | React + TypeScript + Vite；CSS/Tailwind 实现设计组件 | 事项列表、详情、授权、插件管理；UI 不持有来源凭据 |
| 桌面壳 | Electron 主进程 + 最小 preload | 窗口、托盘、通知、系统授权和凭据代理 |
| 业务核心 | TypeScript；utilityProcess 承载应用服务和作业执行 | 领域规则保持为不依赖 Electron 的包；耗时处理不阻塞窗口 |
| 存储驱动 | better-sqlite3 候选驱动；显式 SQL、WAL、外键 | 必须验证 Electron ABI、目标架构、FTS5 编译选项与 SQLite 实际版本；加密驱动在试用前验证 |
| 公共契约 | JSON Schema Draft-07 + Ajv；从 Schema 生成 TS 类型 | IPC、插件事件和模型输出共用版本化定义；不维护第二套手写字段真相 |
| 推理 | ModelProvider + 一个经评测选定的供应商适配器 | 固定请求预算、结构化输出和取消；具体模型型号由同一评测集决定 |
| 工程 | pnpm workspace、electron-vite/electron-builder 候选 | 通过签名、升级及原生依赖打包验证后锁定版本 |
| 验证 | Vitest 规则/回放测试，Playwright 桌面关键路径测试 | 打包版还需测试授权、系统通知、休眠恢复和原生模块 |

Ajv 支持 JSON Schema；选择 Draft-07 是为减少首版契约复杂度，参见[Schema 语言说明](https://ajv.js.org/guide/schema-language.html)。供应商的结构化输出可能只支持子集，适配器负责转换；返回结果仍以本地完整 Schema 校验为准。

SQLite FTS5 首版需专门验证中文召回：不能假设默认分词能识别中文词语。建议为检索生成中文分词字段并测试项目词典；短词、英文标识符与混合语言单独评估。FTS 未命中时，可对限定项目的近期事项提供有上限的候选，不能扫描无限历史。参考 [FTS5 文档](https://www.sqlite.org/fts5.html)。

## 整体架构

### 组件与部署边界

![整体组件架构](diagrams/01-system.svg)

图的文字等价：来源适配器只在授权范围读取事件，经桌面宿主进入应用核心；应用核心调用模型获取建议，再由领域规则决定如何持久化。SQLite 保存事实和结果，UI 通过受控 IPC 查询及提交人工操作。远端仅包括用户选择的数据平台、模型服务，以及确有需要时的授权中转服务。

采用“一个桌面产品、清晰模块、少量隔离进程”的架构。主进程管理系统能力和生命周期；renderer 启用 sandbox、contextIsolation，关闭 nodeIntegration；preload 暴露少量白名单方法，验证 sender、请求参数与返回大小。正文按不可信内容渲染，不执行其中脚本、命令或指令。

应用核心运行于 utilityProcess，独占数据库写入并串行提交短事务。来源网络 I/O 和模型请求可以有界并发，但数据库事务内不得等待模型。主进程与核心通过结构化 IPC 通信，不启动对外开放的本地 HTTP 服务。来源适配器的故障、退出与重启由宿主管理。

首版所谓“后台”是应用留在托盘时继续运行；用户完全退出或电脑关机后停止采集。休眠唤醒和重新启动后依据持久游标补采，页面上显示覆盖缺口。没有独立 OS 服务时，不承诺退出后仍持续工作。

### 模块职责

| 模块 | 负责 | 不拥有的能力 |
| --- | --- | --- |
| Source Adapter | 授权范围读取、分页/游标、事件修订、健康状态 | 改事项、选择最终完成状态 |
| Ingestion | 格式验证、规范化、去重、持久接收 | 依据文本直接执行命令 |
| Understanding / Skill | 承诺、执行、反馈、变更的结构化提取 | 扩大用户承诺或修改权限 |
| Association | 项目、人物、对象和时间范围候选检索，提出关联 | 仅凭相似标题强制合并 |
| Verifier | 对当前条件给出支持、反对、缺失证据的建议 | 绕过核心直接完成事项 |
| Domain / Policy | 状态机、人工优先级、条件版本、证据校验 | 网络采集及 UI 展示逻辑 |
| Query / Reminder | 有引用的查询投影、提醒去重与冷却 | 将通知成功视作业务完成 |
| Storage / Jobs | 原文与修订、事务、租约、迁移、恢复 | 让派生索引成为第二个事项真相 |

### 建议项目目录

以下是拟议职责划分，不表示对应代码已经创建。避免将每个业务函数拆成独立服务。

- apps/desktop：main、preload、renderer、打包与升级配置。
- packages/domain：事项状态、条件、证据、人工纠正规则；不依赖 UI、数据库或模型 SDK。
- packages/application：接收、分析、关联、核验、查询和提醒用例。
- packages/contracts：JSON Schema、生成类型、版本与兼容测试。
- packages/storage：SQLite repository、迁移、作业、outbox、检索实现。
- packages/connectors：飞书、本地 AI 会话、GitHub 等可信适配器。
- packages/plugin-host：manifest、权限代理、声明式执行器、安装升级。
- packages/model：供应商适配、结构化输出、限流与成本记录。
- packages/evals：标注样例、按时间回放、质量对照。
- docs/architecture：RFC、后续 ADR 与流程图源文件。

依赖方向为 UI/连接器等外层通过 application 使用 domain；domain 不反向引用基础设施。contracts 可以被各边界使用，但不包含业务状态写入实现。

## 事项处理流程

![从输入到事项更新](diagrams/02-pipeline.svg)

图的文字等价：事件持久接收后进入作业，提取结构化建议、寻找可能事项，再核对当前条件和证据。满足策略才提交自动变更；不满足则保留部分进展或待确认结果。两条路径都写入可追溯记录，最后刷新清单并按策略提醒。

### 接收、理解与关联

1. Source 输出标准事件。核心验证 source instance、账户和 scope，限制内容大小；以“来源实例 + 外部事件 ID + 修订标识”建立唯一约束。没有稳定修订号时保存内容哈希，并区分删除事件。
2. 同一事务保存事件、创建处理作业、推进可恢复游标；事务失败不确认接收。来源按至少一次交付处理，避免把内存收到了当作已经持久保存。
3. 将较短时间窗内的相关记录合批，提取明确承诺、尝试、反馈、改期或取消。每个提取结果带原始片段位置、事件修订与提取版本；未知截止时间保持空值。源文本中的“忽略规则”等内容只当数据。
4. 先用项目、仓库、参与人和交付对象缩小候选，再检索文本并由模型建议关联或新建。候选过多时保留不确定性。相似度是召回信号，不是同一事项的证明；原始会话中的 AI 建议不能自动变成用户承诺。
5. 生成标准 DecisionProposal：目标事项、预期事项版本、操作类型、条件修订、证据引用、理由和置信信息。模型返回不存在的 ID、无效修订或超范围字段时拒绝执行。

### 条件与状态提交

完成判断面向当前承诺。例如“提交 PR 并回传链接”有两个条件；PR 创建记录只满足第一个。仓库、目标分支、对象及当前条件版本应一致；若承诺要求上线，单凭合并记录不满足要求。模型说“测试通过”不等于工具记录证实测试通过。

核心检查条件是否清楚、证据是否有效且相关、是否有反证、来源是否具备必要覆盖、用户是否允许该类低风险自动完成，以及是否有仍有效的人工覆盖。语义匹配本身仍会误判，规则校验不能将模型判断变成数学证明，因此自动完成能力按场景逐步开放。

提交时比较 task.version、criteria.version 和人工纠正版本；不一致则丢弃过时建议并重新读取。一个事务更新事项、追加 decision 与 task_revision，并写 notification_outbox。提示或通知在事务外执行。对同一输入集、规则版本和目标操作生成幂等键；模型结果可缓存为 proposal，重试优先恢复既有结果。

业务状态为待办、进行中、等待、完成、取消；候选/忽略是收录决定，未知/部分/充分/冲突是证据状态，归档只是显示属性。取消需要取消依据；自动完成证据失效时重新评估并展示原因。人工完成保留来源为 manual，后续证据不足不自动推翻。

合并、拆分、忽略和撤销均产生明确人工决定。合并保留旧 ID 到新 ID 的映射；拆分重新分配条件和证据。纠正按字段、关联或操作范围生效，不用一个永久锁阻止事项所有后续更新。

## 数据与接口设计

### 核心数据对象

| 对象 | 关键字段 | 约束 |
| --- | --- | --- |
| source_instance | kind、account、scopes、credential_ref、cursor、last_success | 凭据仅保存引用；授权范围和读取进度分开 |
| source_event / revision | source_id、external_id、revision、occurred_at、received_at、content_ref、deleted_at | 事件发生时间与接收时间分开；编辑和撤回可追溯 |
| task / task_revision | task_id、project、owner、title、status、version、archived_at | 权威状态只通过领域用例修改 |
| criterion | criterion_id、task_id、version、description、origin_ref、active | 条件变更版本化，不悄悄扩大承诺 |
| evidence_link | event_revision、criterion_version、relation、validity、reason | relation 为支持/反对/相关；引用必须可解析 |
| decision / manual_override | proposal、input_refs、policy/model/prompt_version、actor、scope、supersedes | 能解释变更并保护有效纠正 |
| job / outbox | idempotency_key、state、attempt、lease_until、next_run、error_code | 租约过期可恢复；重试有预算 |

时间统一存 UTC，并保留来源时区及解析依据；“周五”等相对时间按消息发生时间解释，无法消歧不自行补日期。人物和项目先使用来源命名空间 ID，再记录用户确认的跨源映射，不靠同名合并。

协议采用版本化 envelope：schema_version、source_instance_id、event_id、revision、event_type、occurred_at、payload、provenance。本地 AI 记录需保留 user/assistant/tool 角色与会话定位；文件轮转、截断和格式升级分别处理，不能只保存一个永不校验的字节偏移。

### 一致性、检索与保留

SQLite 开启外键、WAL 和 busy timeout，由核心统一调度写入。对已向用户确认的人工操作建议使用 FULL 同步策略；性能需要实际测量，不能靠降低持久性掩盖延迟。WAL 仍只有一个写者，且不适合把活动数据库放在网络共享路径，依据 [SQLite WAL 文档](https://sqlite.org/wal.html)。

搜索索引、摘要及未来向量均是可重建派生数据，保存生成版本与引用。向量服务不可用时，事项查询和人工操作仍可工作；embedding 失败进入重试，不丢弃事项候选。首版不承诺无限历史：输入大小、回溯窗口、队列长度与磁盘额度可配置，达到限制时背压并显示处理延迟。

原文保留周期在试用前确定，设置页同时解释历史可追溯的代价。删除操作清理原文、摘要、索引、模型缓存和含内容的作业；对相关事项标记证据失效并重新评估。防止再次导入只保留最小无正文抑制标识，并允许用户清除。备份和 WAL 的清理必须纳入实现，不能把 SQL DELETE 宣传为即时安全擦除。云端已经接收的数据按供应商实际保留机制说明。

## 插件与信源接入

![插件安装与运行流程](diagrams/03-plugins.svg)

图的文字等价：插件包经 manifest/版本校验、用户范围授权、样例试运行后安装；宿主代理限定读取，并将标准事件交给同一事项流水线。校验失败或试运行失败不会启动正式采集；运行异常触发暂停和诊断。

插件协议分三类：Source 提供事件；Skill 提供有版本的提取模板与规则配置；Verifier 提供条件核验建议。首版开放可安装的声明式 Source 插件，Skill 和 Verifier 先由项目维护可信版本。对外代码插件作为后续能力，不用“一个子进程”冒充不可信代码沙箱。

manifest 至少包括 plugin_id、version、host_api_range、source_type、schema_version、所需域名/文件范围、凭据用途、采样与速率限制。声明式插件通过宿主提供的 HTTP 分页/本地文件模板运行，不支持任意 shell、动态 eval 或任意依赖下载。域名授权需校验跳转目标、私网地址和凭据转发；文件权限需校验规范化路径、符号链接和范围。

安装流程为包结构与路径检查 → 展示权限差异 → 样例输出校验 → 暂存目录 → 原子启用；失败保留当前可用版本。插件升级改变权限必须重新授权。Source 只获得自己的凭据代理和范围，不获得数据库或其他来源全文。停用取消采集与新请求；卸载和删除历史分开表达。

第三方扩展验收：让未参与核心开发的人实现一种不同于内置源的真实分页 HTTP 来源，含修订和恢复，不改 domain/application 核心；再测试第三方模板越权请求被宿主拒绝。若声明式模板无法表达真实来源，应记录缺口，不能用静态 JSON 样例冒充通用扩展验证。

### 首批来源的接入约束

| 来源 | 首版接入建议 | 开发前必须核验 |
| --- | --- | --- |
| 飞书 | 选定对话范围的官方 API；平台支持且权限允许时结合事件增量与补采 | 用户/机器人身份、租户审批、历史与编辑撤回可见性；安装本机 CLI 不代表产品用户自动具有同等权限 |
| 本地 AI 会话 | 先选一种实际可读的会话格式，用户指定目录，只读导入 | 角色和工具结果语义、文件轮转、跨版本格式；格式属于适配器实现细节 |
| GitHub | 对选定仓库轮询 PR/检查等交付记录，使用缓存和退避 | 最小权限、私有仓库覆盖、API 限流、PR 创建/合并/测试/部署的语义区别 |

飞书接口入口见[获取历史消息](https://open.feishu.cn/document/server-docs/im-v1/message/list)；本轮网页未返回可读权限细则，故实际可见范围仍为接入门禁，不宣称可以读取全部个人消息。若关键承诺对话不可见，应限定场景或改为用户主动导入，并如实标明非自动覆盖。

桌面通常无法直接接收公网 webhook。首版以可恢复轮询为基础，不能在架构中画一个公网回调就假定桌面可达。GitHub 可评估官方 device flow，见[OAuth 授权文档](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)。任何需要保密 client secret 的接入不得把共享 secret 打包进桌面；若飞书所选授权方式必须中转，增加最小授权服务，仅处理授权交换，单独说明服务端数据与部署责任。

## 失败处理、隐私与恢复

| 情况 | 处理与恢复 | 对用户的影响 |
| --- | --- | --- |
| 模型超时、限流、Schema 无效 | 有界退避、记录失败码；恢复后重跑原作业 | 展示处理延迟，已有事项可用 |
| 核心或插件崩溃 | 宿主重启；过期作业租约回收；游标补采 | 显示最后成功时间，不伪造实时覆盖 |
| 重复、乱序、迟到事件 | 修订与幂等键去重；按语义时间重评估相关事项 | 不因最后接收到而覆盖正确计划 |
| 人工编辑与模型返回竞争 | 乐观版本检查；过期 proposal 不提交 | 保留用户修改，后台重新评估 |
| 撤权或暂停 | 停止新读取；取消排队推理，检查在途结果授权版本 | 保留/删除历史由用户选择；撤权前已发出请求无法追回 |
| 通知投递时进程崩溃 | outbox 恢复，应用内通知唯一 ID；系统通知尽量复用 ID | OS 提醒存在重复窗口，不承诺端到端恰好一次 |
| 磁盘满、迁移失败 | 停止接收确认与自动更新，保留诊断；修复后补采 | 明确数据未接收，避免无声丢失 |

来源文本、插件模板、模型输出分别处于不可信输入边界。模型请求只含当前用例所需片段，禁止隐式上传全库；日志默认不记录正文、密钥、提示全文。IPC、路径、网络访问和证据引用都需在宿主侧校验。

凭据使用操作系统保护的存储能力，Electron safeStorage 在 macOS 使用 Keychain 相关能力，见[官方说明](https://www.electronjs.org/docs/latest/api/safe-storage)。这不等于数据库已加密。真实敏感数据试用前验证加密 SQLite 驱动及备份加密、钥匙丢失恢复策略；开发原型可以使用脱敏样本与普通 SQLite。若加密驱动兼容性尚未通过，则不把“本地加密存储”列为已交付能力。

首版自建服务不是事项数据的必经之路；只有授权中转或未来同步明确需要才增加。模型供应商、发送范围、保留策略与费用应可见。关闭云推理时仍支持列表和人工操作，自动理解暂停；本地模型适配通过质量与资源验证后才宣称离线自动理解。

## 实施顺序、验证与上线

### 分阶段推进

| 阶段 | 交付物 | 通过条件 |
| --- | --- | --- |
| A 接入与打包探针 | macOS 最小壳；三类候选来源样例；授权与 SQLite 原生模块验证 | 真实承诺、执行、交付链路可读；明确缺失范围；安装包可启动 |
| B 可回放闭环 | 数据契约、事件/作业、状态与人工纠正、只读清单 | 重复、撤回、失败与人工竞争样例通过；先观察建议，不自动完成 |
| C 有限自动维护 | 条件核验、提醒、来源健康、删除与恢复 | 已定义低风险场景质量过线；权限和可追溯硬约束通过 |
| D 扩展与小范围试用 | 第三方声明式来源、签名升级、成本与资源仪表 | 无核心修改接入；试用净收益成立；故障可诊断恢复 |

### 验证口径

先构建 PRD 建议的约 30 条完整链路，每条按时间前缀回放，判断只能看到当时已有证据，避免用未来结果美化准确率。对照单次提取和简单规则，分别报告来源覆盖、漏记、误建、错误关联、错误完成和人工维护耗时；错误完成必须同时报告自动完成覆盖率。

核心集成测试覆盖：同一事件重复 10 次仅一次业务变更；任务人工编辑与模型返回竞争；来源编辑/撤回后证据失效；模型解析失败恢复；提交成功后进程崩溃重启；插件越权拒绝；删除后索引及缓存不可再召回。打包测试覆盖托盘、权限拒绝、睡眠唤醒、升级迁移和网络断开。

观测记录包括 trace_id、来源/作业/事项 ID、阶段耗时、重试次数、Schema 错误、关联纠正、自动完成撤销、队列积压、每活跃用户推理成本；默认不附正文。资源按空闲、持续增量、历史回补三个负载分别测量 CPU、内存、磁盘增长和事件到清单延迟。具体预算由试用设备与频率确定，必须在扩大试用前冻结，本文不虚构已测数值。

### 发布与回滚

采用签名安装包和分阶段发布。数据库迁移前使用一致性备份机制，不复制一个仍在写入的裸 DB 文件。迁移带版本号、失败停止启动自动写入，并提供恢复入口；不可逆迁移不直接降级旧程序。恢复旧备份会丢失备份后人工变更，因此降级前先导出新增人工记录并明确恢复范围。

规则、模型和插件版本分别记录，可独立回退；规则回退不盲目批量重放并覆盖现有事项。发现错误自动完成时，先关闭对应场景策略，再对受影响 decision 提出可审阅修正，保留人工决定。恢复成功以数据一致、来源进度可续、无重复变更和用户纠正仍有效为判据。
