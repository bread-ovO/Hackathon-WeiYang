# 原生交互模块评估（X04）

结论：保留 Electron 桌面壳，暂不新增 Swift UI 模块。已测到窗口恢复的帧调度长尾及桌宠销毁后重建的延迟；现有证据更支持先优化生命周期与调度，再测同一链路。没有证据证明重写桌面壳可以解决它们。

## 实测

设备为本机 Apple M4、16 GiB、macOS，精确系统与 Electron/Chromium 版本在[原始报告](../evals/results/ten-closeout-2026-09-15/native-interaction.json)。隔离空工作区与 Hiyori，每段 30 次采样；同期可能有其他应用和模型验收运行，数据不是空闲实验室基准。

| 测量段 | 中位数 | P95 |
| --- | ---: | ---: |
| 主窗口恢复至两帧后（含测试通信） | 50.73 ms | 534.57 ms |
| 其中 show/focus 调用 | 9.76 ms | 28.57 ms |
| 其中等待两帧 | 44.87 ms | 529.94 ms |
| typed preload 健康请求往返 | 1.97 ms | 6.78 ms |
| 桌宠重新显示至 ready | 850.04 ms | 885.35 ms |
| 其中 show 请求返回 | 447.34 ms | 459.72 ms |
| 其中等待 ready 状态 | 401.09 ms | 416.11 ms |

这些分段的百分位分别计算，不能把各段 P95 相加当作整体 P95。第一次未拆段测量的恢复中位数为 532.60 ms；[首轮数据](../evals/results/ten-closeout-2026-09-15/native-interaction-initial.json)也保留，用于说明恢复调度存在明显波动，而不是只选最好一次。

## 测量含义

主窗口路径复现 `trayHost.restoreWindow` 的 `show()/focus()`，再等待两次 renderer requestAnimationFrame；不包含操作系统托盘菜单的点击命中、输入设备延迟和首次启动。因而它是这段软件链路的测量，不是全局快捷键端到端的成绩。

桌宠 `hide()` 当前会执行 `stop()` → `rendererGone()`，释放并销毁 renderer；再次 `show()` 会重新准备窗口和资源。这里是同一次应用运行中的重复显示，资源已导入，但并非复用已加载 renderer 的纯 show。原始报告的 warm 指同次运行，不能理解为热 renderer。

测量入口：[native-interaction-benchmark.spec.ts](../../tests/desktop/native-interaction-benchmark.spec.ts)；代码路径：[主窗口恢复](../../apps/desktop/src/main/index.ts)、[桌宠控制器](../../apps/desktop/src/main/pet/desktop-controller.ts)、[桌宠窗口生命周期](../../apps/desktop/src/main/pet/pet-window.ts)。

## 决策与后续门槛

- Native show/focus 和普通桥接都明显短于恢复长尾；先调查 renderer 从隐藏状态恢复的帧调度，不用 Swift 重写来代替归因。
- 桌宠的主要可见等待包含资源及 renderer 重建。下一步可单独评估“隐藏时暂停、保留实例”与“彻底释放”的内存和恢复速度取舍，必须保留撤权、模型切换、资源失效和崩溃隔离保障。本批没有偷改这些生命周期策略。
- 对热恢复暂设 P95 <100 ms、重复显示 P95 <300 ms 为后续优化目标，本次测量尚未达到，不能把目标写成已实现。
- 只有性能剖析证明系统窗口/权限 API 是持续瓶颈，且 Electron 侧优化后同机同场景仍失败，才做小范围 Swift 模块原型；共享业务逻辑和 typed bridge 保留。
- 本轮未测 Windows/Linux，也未测操作系统托盘点击或全局快捷键，不外推三平台交互性能。

X04 的交付是测量与技术决策。具体提速开发和跨平台性能矩阵不在此项完成范围内。
