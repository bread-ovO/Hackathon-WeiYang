# 版本发布

推送 `v主版本.次版本.修订号` tag 后，GitHub Actions 自动构建并发布安装包。普通分支提交和 PR 不触发这条工作流，也不运行全套 E2E。工作流见 [release.yml](../../.github/workflows/release.yml)。

## 安装包

| 平台 | 架构 | 文件 |
| --- | --- | --- |
| Windows | x64 | `BUGU-版本-Windows-x64-Setup.exe`，支持选择安装目录 |
| macOS | Apple Silicon | `BUGU-版本-macOS-arm64.dmg` |
| macOS | Intel | `BUGU-版本-macOS-x64.dmg` |
| Linux | x64 | `BUGU-版本-Linux-x86_64.AppImage`、`BUGU-版本-Linux-amd64.deb` |

各架构使用对应的原生构建机器，避免带入其他架构的 SQLite 或 Swift 二进制。macOS runner 使用 `macos-15` / `macos-15-intel`，平台定义见 [GitHub runner 文档](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)。

安装包首次启动为空白个人工作区，保留来源连接入口和默认桃濑日和。打包前下载并验证固定哈希的 Live2D 资源；所有平台均经过现有打包钩子的模型资源检查。Linux 需要 `libarchive-tools`，工作流自动安装。

## 发一个版本

先确认需要发布的修改已经合入主仓库 main，再在该提交上创建 tag：

```bash
git fetch upstream main
git tag -a v0.1.0 upstream/main -m 'BUGU v0.1.0'
git push upstream v0.1.0
```

安装包版本直接取 tag，作为 electron-builder 的 `extraMetadata.version`，不需要工作流另行提交版本号变更。`v0.2.0-rc.1` 这类 tag 会标为预发布。

工作流固定 Node 22、pnpm 10.34.5 和 Actions 提交哈希。四组构建全部成功后，汇总任务检查五个安装包是否完整、拒绝空文件和额外文件，并生成 `SHA256SUMS`。最后先创建草稿、上传全部附件，再公开 Release。

只给汇总发布 job `contents: write`，使用仓库自带的 `GITHUB_TOKEN`，不需要额外 PAT。Release 页面位于 [GitHub Releases](https://github.com/bread-ovO/bugu-notes/releases)。

## 验证和重试

- Actions → **Release installers** → **Run workflow**：输入版本 tag 格式的版本号。这种手动运行只构建与校验，在 Actions 中保留安装包 7 天，不创建 tag、不发布 Release。
- 某个平台失败：在该 run 重跑失败 job。其余成功的安装包继续可用于同一个 run 的汇总；如果附件已过期，重跑所有 job。
- 上传失败：保留草稿，重试可覆盖草稿中的同名文件。
- 已公开版本拒绝覆盖。需要修订已发布的代码时，使用下一个版本 tag，不移动旧 tag。

本地可用 `node --test scripts/release.test.mjs` 检查版本解析和附件完整性校验；`pnpm package:release --mac --arm64` 可构建当前机器对应的安装包。首发前建议手动执行一次跨平台构建。

## 签名范围

当前未配置 Windows 代码签名、macOS Developer ID 签名与 Apple 公证。这些安装包可以分发，但系统可能提示无法验证发布者。代码签名与公证需要后续接入团队证书；发布流程不会伪装成已签名安装包。
