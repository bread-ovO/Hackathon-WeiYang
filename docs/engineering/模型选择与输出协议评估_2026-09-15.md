## 同集比较方法

使用 `time-prefix-v1` 第一条链的 6 个独立前缀：承诺、尝试、失败、交付反馈、改期、取消。每个请求只发送当时可见的消息，经过提取和复核两次真实模型调用，再校验结构、逐字引用、目标数、阶段、最近变化及截止时间。两客户端比较均使用 task-analysis-v4 的相同原文和提示；修复变化优先级后的 v4.1 另跑完整 156 前缀，不混入这张对照表。

## 选择理由与适配范围

1. Codex 同集有有效结构化结果，质量与引用都可核对，适合本机继续验收；保持无工具的推理沙箱、取消和超时上限。
2. 两轮调用能补检漏项，但也增加延迟和额度消耗。自动整理按既有增量窗口工作，不因打开列表重复调用；不以规则代替失败的模型。
3. Responses API 走 `/responses` 的结构化输出；Chat Completions 走 `/chat/completions` 的 JSON Schema。两者的 endpoint、请求体、返回结构、错误/截断处理和凭据边界由定向契约测试覆盖。本轮没有额外 API Key，不把模拟服务测试说成真实云 API 质量测试。
4. Claude 本轮只确认入口可启动但未取得结果。保留明确错误与重试操作，不静默切换服务。供应商切换必须在模型设置完成，避免内容发往意料外的服务。
5. Kimi 保持关闭选项，待可用的隔离非交互协议和实际成功样例后再放行。

## 输出协议

当前 `task-analysis-v4.2` 返回具体目标、阶段、下一步、已有事项 ID、带引用的截止建议、证据数组和最近变化类型。存量结果没有 `changeKind` 仍可读取；真实模型 Schema 要求该字段。取消优先于明确改期，改期优先于同句的失败/反馈；其余信息保留在下一步和原文。v4.2 进一步约束同一交付目标下的环境确认和准备步骤，避免仅因执行者不同就另建事项。v4.1 完整前缀复测为 156/156；v4.2 已通过真实客户端 UI 复测及 3 个目标粒度回归，但本批未在 v4.2 上重复完整 156 项，不混用版本成绩。

供应商输出一律不可信：字段白名单、数量/长度、精确消息引用、项目内 ID、日期形状经校验后才持久化；语义阶段是待复核建议，不能直接更新人工业务状态。失败、超时、关闭不回退到规则提取。

## 结论边界

本评估完成了当前本机配置下的选型和适配范围决策，不代表全部账号/网络的 Claude 可用性，也没有完成所有供应商真实 API 的横向基准。时间前缀集含 24 个业务对象套用同一 6 阶段链和 6 条反例链，用于检查时间泄漏与变更覆盖；不能把该固定集得分外推为真实聊天 99% 准确率。
