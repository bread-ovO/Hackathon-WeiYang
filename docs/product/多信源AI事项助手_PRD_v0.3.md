# 多信源 AI 事项助手｜PRD（产品需求文档）v0.3

飞书版本：[PRD（产品需求文档）v0.3](https://my.feishu.cn/docx/JQ11dTz4ioqXcExWlq2cMH9zn5e)

状态：产品讨论稿。日期：2026-09-12。面向：项目发起人、产品、设计、研发与测试。

本版重点回答：产品解决什么问题、创新体现在哪里、客户为什么愿意使用和付费。功能体验以 AirJelly 为参照，主要开源竞品与架构参照为 MineContext。本文定义用户价值与首版行为；具体技术栈、详细界面和研发排期另行制定。

## 产品概述

**一句话定位：一个可扩展的个人事项助手，在用户授权后，从工作交流与 AI 协作中发现需要跟进的事情，持续关联执行和交付记录，让用户知道“答应了什么、做到哪一步、还缺什么”。**

用户在聊天里答应修复问题，转到 AI 编程工具完成工作，再回到原对话反馈。产品把这段分散的过程维护成同一个事项，并在恰当的时候提醒用户补上最后一步。

产品价值有三个层次：帮助用户少漏事；减少手动录入和维护清单的时间；随着用户新增工作工具，继续覆盖其工作过程。

我们希望形成的核心体验是：**不用反复回想和翻找，也能对自己正在承担的事情心中有数。**

## 当前自动整理约定（2026-09-15）

- 自动收录统一经过用户启用的真实大模型；删除规则建任务的替代路径。模型未配置或失败时保留原文，并显示原因。
- 用户授权后后台整理，不要求逐个选择会话、点击分析。任务带来源进入待确认清单，详情可回看最初请求及后续进展依据。
- 长会话分段处理，同一目标的补充、测试和反馈保持为一项。模型阶段建议与人工业务状态分开，不因为模型声称完成就自动销项。
- 本地质量门槛为任务精确率、召回率和会话完全正确率分别至少 99%。固定合成语料达标不等于真实用户准确率，需保留全部失败记录及验证边界。详见 [评测方法](../evals/JSONL任务提取本地评测.md)。

## 我们要解决什么问题

### 问题发生在工作工具之间

用户的工作过程已经跨越聊天、AI 会话、文档和代码平台。承诺在一个地方提出，行动在另一个地方发生，交付与反馈又回到其他渠道。单个应用通常只能看到其中一段，用户需要自己把这些片段连起来。

以下是目标问题假设，来自项目讨论与工作流分析，尚未经过系统用户访谈验证：

| 用户问题 | 具体表现 | 产品要交付的结果 |
| --- | --- | --- |
| 忘记记下承诺 | 在聊天中答应处理，切换应用后没有录入待办 | 授权范围内的明确承诺可以被及时发现 |
| 清单很快过时 | 已经改期、交付或取消，清单仍停留在旧状态 | 后续信息持续更新原事项 |
| 做过不等于做完 | 代码已改，但测试、部署或反馈还没完成 | 明确已满足和未满足的约定条件 |
| 同一件事重复出现 | 聊天、AI 总结和会议纪要各产生一条待办 | 多个来源共同维护一个事项 |
| 新工具造成新的遗漏 | 工作换了工具，助手无法接入，只能手工搬运 | 用户可以安装适配器扩展覆盖范围 |
| 自动化反而增加负担 | 用户每天删除误建任务、纠正错误完成、关闭无用提醒 | 总维护时间下降，提醒可解释且可控制 |

### 首批目标客户

**首批聚焦频繁使用 AI 工具、同时承担跨应用交付责任的个人工作者，优先从开发者和技术负责人验证。** 他们有明确的外部承诺，也有相对可追溯的执行记录，适合验证完整事项链路。

目标用户需要满足的不是某个职位标签，而是以下工作特征：经常在协作聊天与 AI 工具之间切换；同时推进多件事；需要向其他人交付或反馈；已经为记忆和清单维护付出时间；愿意授权限定范围的数据。

早期以个人为使用者和潜在付费者。团队可能是后续采购方，但企业管理员是否允许接入、团队需要什么权限和管理能力，尚未验证。首版不依赖团队统一采购才能产生价值。

只有单一清单需求、没有明显跨应用工作过程，或无法授权关键渠道的用户，不是首轮验证对象。产品必须允许覆盖不足，不能承诺读取每个应用的全部信息。

### 最核心的用户任务

“当我在多个聊天和 AI 工具之间推进工作时，帮我记住自己承担的事情，并根据后续记录告诉我还差什么，让我不用在交付前重新翻遍所有记录。”

## 产品目标与边界

首版目标是证明：在真实可读取的数据范围内，产品可以持续维护少量真实事项，而且用户为它付出的时间小于节省的时间。

产品应让用户获得四个可观察结果：重要承诺被记录；同一事项的进展保持连续；完成或变更有可追溯依据；用户能够快速纠正且不被系统反复覆盖。

首版提供个人事项管理、询问、来源与插件管理、轻提醒和事项时间线。至少用两个真实信源验证同一事项的关联；交付核验优先选择有明确记录的场景。首批候选是飞书授权对话、一种本地 AI 会话及一种交付记录，实际组合以权限与格式验证结果为准。

首版不建设通用知识库、完整团队项目管理、插件支付商店或全平台采集；不默认开启屏幕和麦克风；不自动替用户发送消息、修改代码或执行外部业务操作。外部 Agent 查询上下文、日报与草稿辅助可在后续阶段增加。

## 创新点是什么

### 创新一：从生成待办，推进到持续维护同一个事项

单次提取回答“这段话里有哪些待办”；本产品持续回答“这个承诺后来发生了什么”。聊天中的要求、AI 会话中的执行尝试和交付记录应该围绕一个事项共同积累，而非每次生成新清单。

用户感知到的创新是：不需要再扮演多个工具之间的人工同步员。项目改期、执行失败、部分交付或取消时，助手能解释这件事的变化。

**验证方式：**对同一段跨应用工作过程，比较重复事项、错误关联、状态错误和人工维护时间。只有优于单次提取或简单规则，才证明这项价值成立。

### 创新二：按约定条件判断完成，并保留证据

产品区分建议、明确承诺、执行尝试和交付结果。完成标准来自用户实际承担的要求，不由模型自行加码，也不因为助手说“完成了”就自动销项。

例如，约定是“提交 PR 并反馈链接”，不额外要求生产部署；约定是“上线验证并告知同事”，则合并代码只构成部分进展。缺少记录时说明“尚未找到证据”，不能断言用户没做。

用户感知到的创新是：可以相信列表中的状态，并知道为什么。系统长时间没有观察到活动，也只应降低活跃度或提示确认，不能因此认定义务完成。

**验证方式：**在相近自动化覆盖下，错误完成更少；每次自动完成都有对应条件和来源，且能撤销。

### 创新三：让用户扩展工作覆盖，同时沿用统一事项规则

用户可以安装来源插件接入自己的工具；进阶用户修改配置；开发者通过公开结构定义和适配器扩展。AI 可以辅助生成插件，但插件必须经过校验和试运行。

新增来源之后，用户仍使用同一个事项列表、同一套纠正与完成机制。插件提供数据和判断建议，宿主负责最终状态与权限管理。

用户感知到的创新是：助手能适应自己的工具组合，而不必迁移全部工作。插件作者的价值则是接入新来源时不必重新开发事项系统。

**验证方式：**不熟悉核心实现的人可以接入一种有实质差异的来源，不修改宿主核心，并且接入后的维护成本可接受。普通用户不应被要求学习配置语言。

### 创新边界与竞争定位

后台采集、自动待办、Skills 和 AI 辅助扩展已有先例，本项目不以“首创”作为卖点。AirJelly 实机已展示主动帮助、Skills、记忆与外部上下文入口；MineContext 提供采集、处理、上下文与消费分层。相关事实见本项目的实机与源码调研。

**拟验证的差异化是三者的组合效果：可扩展的覆盖、连续的事项理解、低维护且可追溯的状态。** 这仍是产品假设，不能在测试前宣传为已经领先竞品。

## 为什么能吸引客户

### 使用动机：解决一个具体而频繁的麻烦

第一吸引力是减少交付遗漏，尤其是“事情做了，最后一步没跟上”。第二吸引力是降低维护负担，让已有的聊天和执行记录自然成为进展依据。插件扩展带来的是长期适配能力，对普通用户应体现为可安装的工具支持，而非技术概念。

建议的产品介绍是：“把散落的承诺接起来，帮你跟到交付。” 首次演示应展示一件事的完整变化，而不是展示信源数量或技术架构。

### 首次价值：尽快看到一件真实有用的事

用户选择一个具体工作场景，连接愿意授权的来源。产品说明读取范围和是否已有数据；找到明确事项后，展示原始承诺、已知进展和下一步缺口。用户可以一键纠正或忽略。

第一次体验成功的标志，是用户认可“这确实是我需要跟进的事，而且它替我省了一次翻找或记忆”。如果没有足够数据，应说明原因并允许有限范围的手动导入，不能生成看似丰富但无关的清单。

### 留存动机：每天少做一部分清单维护

| 使用阶段 | 用户为什么回来 | 产品需要证明什么 |
| --- | --- | --- |
| 初次使用 | 想确认有没有漏下承诺 | 找到真实相关事项，说明来源 |
| 持续使用 | 想知道现在最需要跟进什么 | 状态跟随新信息变化，提醒不过量 |
| 新项目或新工具 | 希望助手继续覆盖工作 | 扩展接入可用，历史事项仍连续 |
| 长期使用 | 已形成可信的事项记录与个人处理习惯 | 纠正得到保留，数据可导出、可删除 |

长期价值应来自可靠性和持续节省时间，而非依靠阻止用户迁移。历史积累与场景规则可能形成优势，但插件生态和网络效应尚未建立。

### 付费动机与商业化假设

潜在付费理由是更少的真实遗漏和更低的日常管理成本。客户是否愿意付费，取决于这种收益能否重复出现，以及授权、成本和稳定性是否可接受。

可测试个人订阅模式，并探索按接入范围或自动维护能力区分方案；当前不确定价格、免费额度或套餐。后续通过持续使用和真实付费试验验证，而非只询问“你觉得这个想法好不好”。

首批获客可从能展示真实交付链路的 AI 开发者试用开始。社区分享重点放在可复现的场景和适配器，不将“用户会主动贡献插件”作为首版成立的前提。

### 哪些因素会让客户放弃

如果关键渠道无法授权、采集覆盖不足而不说明、频繁误建与误完成、需要每天清理候选，或系统消耗明显影响工作，用户可能回到原有清单。客户吸引力必须与这些成本一起验证，不能只统计新建事项数量。

## 核心用户场景

### 场景 A：提交修复并反馈

1. 用户在授权对话中承诺：“周五前提交修复 PR，把链接发给你。”
2. 助手收录同一事项，记录责任人、截止依据和两项完成条件：PR 已提交、链接已反馈。
3. 用户在 AI 工具中修复问题。AI 建议额外重构，助手将其作为建议，不扩大已承担的范围。
4. 工具记录显示测试失败，助手记录失败与后续尝试，事项保持未完成。
5. 出现正确仓库中的 PR，助手更新为部分完成，提示尚缺反馈证据。
6. 原对话出现向承诺对象发送 PR 链接的记录，且符合当前条件，助手按用户策略完成事项。
7. 用户可查看依据、撤销判断或手动完成；若反馈发生在不可见渠道，不自动判定用户未反馈。

### 场景 B：计划改变

用户在后续对话中明确将截止时间改到下周，或取消交付。助手更新原事项并保留变更依据。如果来源冲突，显示待确认，不以最后到达的一条记录机械覆盖。

### 场景 C：接入新的工作工具

用户安装适合该工具的来源插件，查看读取范围并授权。插件有可用样例时先验证，再开始采集。新来源产生的事件可以关联已有事项；插件失败时显示覆盖缺口，原事项仍可查看与手动维护。

## 首版行为需求与验收

P0 表示首版必须具备；P1 表示核心链路通过后再进入。

| 编号 / 优先级 | 用户触发与产品行为 | 验收结果 |
| --- | --- | --- |
| R01 / P0 来源接入 | 用户选择来源并授权后，展示读取范围、数据状态和断连信息 | 不支持或未授权的范围明确可见；暂停后停止新采集 |
| R02 / P0 事项发现 | 授权信息中出现用户承担的明确要求时，收录事项并附原文 | 明确承诺可收录；AI 未被接受的建议不自动成为正式事项；未知截止留空 |
| R03 / P0 跨源关联 | 新执行或交付记录到达时，结合项目、对象和来源判断是否属于原事项 | 重复消息不重复建项；同名不同项目不因标题相似被直接合并 |
| R04 / P0 进展维护 | 新证据支持进展、改期或取消时，更新原事项 | 变化有依据；部分完成不等于整项完成；冲突明确显示 |
| R05 / P0 完成核对 | 当前约定条件均有支持证据且策略允许时自动完成 | 每次自动完成可定位到条件与证据；失败或过期证据不能错误支撑完成；允许撤销 |
| R06 / P0 人工纠正 | 用户编辑、忽略、合并、拆分、手动完成或撤销 | 结果立即可见；旧事件重放不推翻仍有效的人工选择 |
| R07 / P0 低打扰提醒 | 临近约定期限、出现明确阻塞或需要决策时提示 | 普通新增默认静默；可稍后提醒、静默或关闭；重复提醒受控 |
| R08 / P0 查看与询问 | 用户查看或询问“这件事还差什么” | 返回已确认进展、待满足条件及来源；覆盖不足时说明，不补造事实 |
| R09 / P0 插件扩展 | 用户安装、启停来源插件；开发者按公开规范适配新来源 | 至少两个真实来源遵守相同协议；第三方示例接入不改核心；失败可诊断 |
| R10 / P0 数据控制 | 用户删除、导出数据或撤销来源授权 | 删除与导出有明确范围；撤权停止后续采集；失效证据不伪装为仍可访问 |
| R11 / P1 外部上下文 | 用户允许其他 AI 按需查询事项上下文 | 调用范围受控，有召回记录和引用 |
| R12 / P1 日报与草稿 | 用户需要回顾或准备反馈内容 | 基于已有事项生成结果；对外发送仍由用户完成 |

首版自动完成只开放已定义、可回放验证的低风险场景。高影响事项或条件不明确的事项保留人工决定，不能用所有事项一律确认的方式转嫁维护负担。

## 信息结构、状态与异常

主要入口包括事项列表、事项详情、来源与插件页、询问入口。事项详情优先回答三个问题：为什么被记下、已经确认什么、还缺什么。

业务状态统一为待办、进行中、等待、完成、取消。收录候选与忽略属于收录决定；未知、部分、充分、冲突属于证据状态。归档只改变展示，不替代完成。

对长期没有新信息的事项，产品可降低展示优先级或请求确认；对已经完成后出现的新问题，应判断是新事项、复发还是原先误判，不无限重开历史记录。

| 异常 | 用户应看到什么 | 系统应如何处理 |
| --- | --- | --- |
| 来源断连或授权不足 | 哪段范围暂不可见，最后成功时间 | 保留已有事项，停止给出无依据的否定判断 |
| AI 调用或解析失败 | 处理延迟或失败状态 | 保留输入以便重试，不静默丢失候选 |
| 消息编辑或撤回 | 相关证据已变化或失效 | 重新评估受影响条件，保留变更记录 |
| 人物、项目匹配不确定 | 无法确认关联对象 | 暂不自动合并，必要时提出一次明确问题 |
| 线下完成不可见 | 尚未找到完成证据，可手动完成 | 尊重人工结果，避免反复恢复 |
| 插件停止工作 | 插件错误与覆盖缺口 | 不影响其他来源和手动事项维护 |

本地保存与云端推理须分别说明。插件不能因安装就获得全部历史或任意外部操作权限。质量验证还应覆盖授权边界、数据删除、恢复、资源消耗与延迟；具体性能目标在试用设备与真实采集频率确定后由研发和产品共同校准。

## 如何判断产品是否成立

先建立约 30 条经授权、脱敏的完整事项链路，用于发现规则错误；再开展小范围真实使用。30 条是测试启动建议，不是准确率的统计保证。

对照至少包括：用户现有方法、单次 AI 总结加待办提取、相同信息下的简单关联规则，以及权限允许时的 AirJelly 完整体验。采集覆盖与给定数据后的判断效果分开报告，不能混成一个准确率。

| 验证问题 | 指标口径 | 决策用途 |
| --- | --- | --- |
| 是否减少遗漏 | 用户确认应跟进但未被记下的事项占比，同时报告不应创建的事项占比 | 防止靠大量建项掩盖漏记 |
| 状态是否可信 | 自动完成中当时未满足约定条件的比例，同时报告自动维护覆盖 | 防止靠不自动处理制造高准确率 |
| 是否省时间 | 每用户每日录入、纠错、阅读无效提醒、配置和排障的总时间 | 与用户原有方法比较净收益 |
| 是否愿意持续使用 | 首次确认有用事项、后续持续使用、关闭来源或弃用的原因 | 判断首次价值和留存动机 |
| 扩展是否有价值 | 独立接入成功、耗时、核心修改和后续维护量 | 判断插件是实际收益还是负担 |
| 是否愿意付费 | 完成试用后的真实购买或续用行为，附使用收益与成本 | 判断商业化，而非用兴趣表达代替需求 |

准确率、时间节省和留存的目标值尚未确定。建议由产品负责人在首轮样例标注与试用基线建立后、扩大试用前确定；负责人待项目指定。首版硬性验收包括自动变更可追溯、人工纠正不被旧事件覆盖、重复回放不重复建项、来源权限边界有效。

继续投入的信号是：相近覆盖下，用户少漏事、少维护，并愿意持续连接来源；扩展新工具的收益超过成本。若用户只喜欢摘要、不信任状态，或新来源主要增加噪声，应收窄为更具体的场景，而非继续增加功能入口。
