# AI 事项分析验收

本轮先编写测试，再实现模型调用与桌面确认流程。所有自动化样例都是虚构对话，不读取个人聊天或凭据。

## 语义用例

可执行语料见 `tests/fixtures/llm/task-analysis.ts`。覆盖祈使句提取、同任务补充、交付与验收区分、明确验收、交付驳回、取消、多任务、知识询问、寒暄、助手建议、引用示例、提示注入、缺上下文、英文指令及验收范围。

每个样例断言候选数量、建议阶段和必要消息引用。它不等于对标题质量、所有补充条件或真实会话准确率的完整测量。助手单独建议由应用入口直接排除，不调用模型。

模型样例仅用于开发回归，不能将通过比例宣传为真实用户准确率。v2 的 15 条开发回归已通过（包含两条不调用模型的助手消息入口过滤）。首轮 Qwen3 4B 的失败记录保留在本目录。Qwen2.5 7B 的结果见相应 JSON。实机四轮对话额外暴露“请验收”误判成“已验收”，因此 v2 补了明确用户确认的保守校验和回归测试。

## 必须守住的边界

- 模型仅输出建议，没有项目 ID、任务 ID 或数据库操作权限。
- 引用必须对应本次输入中的消息，且逐字匹配原文。
- 用户完成确认与取消确认需要明确依据，不能用助手自称完成替代。
- accepted/cancelled 可以没有下一步，不要求模型虚构后续动作。
- 非法 JSON、未知字段、伪造引用、重复引用、超预算输入输出应拒绝。
- 超时、取消、迟到响应不得产生成功结果。
- 同一分析重复确认只创建一个任务，重启保留确认记录。
- 分析期间来源撤权、内容更新，落库与确认均拒绝过时结果。
- 同源、同标题、同一原始请求引用再次确认复用原任务，不覆盖人工状态。

## 当前实现范围

连接页顶部“AI 事项分析”选择一个已授权本地来源，读取最多 64 条、24,000 字符的最近完整消息。在固定本机 Ollama 端点运行 Qwen2.5 7B，60 秒超时。部分上下文明确提示；新消息过长导致没有完整可分析消息时拒绝执行。

结果按模型/协议/输入指纹持久保存。用户确认后以人工决定创建待办事项，不自动应用模型阶段；模型阶段、下一步和引用保存在分析记录中。事项详情展示分析时的下一步建议和可展开原文；这些历史建议不自动覆盖用户最新状态。

此版本尚未将后台规则处理替换为全历史语义消费，也没有实现跨会话/跨渠道自动归并、模型服务配置界面、云端模型授权或自动完成。同一引用中的不同标题保留为不同事项；不同措辞的相同目标仍可能需要人工合并。旧规则与模型建议可能重叠，路演隔离工作区暂停规则处理。

## 运行

```sh
ollama pull qwen2.5:7b
pnpm test tests/unit/task-analysis.test.ts tests/unit/task-analyzer.test.ts
pnpm test:storage task-analysis-integration
pnpm exec esbuild tests/eval-task-analysis.ts --bundle --platform=node --format=esm --outfile=/tmp/bugu-eval.mjs
node /tmp/bugu-eval.mjs /tmp/bugu-model-eval.json
```

模型回归是显式运行的本机网络测试，不加入默认单测或全量 E2E。单个用例可通过 `BUGU_EVAL_CASE` 选择。

协议参考：[Ollama Chat API](https://docs.ollama.com/api/chat)。服务端仅使用兼容的结构 Schema，完整长度限制和引用校验仍由应用执行。
